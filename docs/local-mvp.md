# ローカルMVPの運用ガイド

## 実装範囲

プロデュースメモリーの登録・比較・バックアップをローカルで利用できます。
Cloudflare へのデプロイ、本番接続、公開先での動作確認は行っていません。
マスターは同梱 JSON、所持メモリーは IndexedDB に保存します。D1 は採用していません。

- 通常プロデュースカードの R・SR・SSR を328種収録（強化前後は別 ID）。
- 対応カスタム89種、HIF の発動対象と固定効果105種を収録。
- 同一カードの複数登録、編集、複製、削除、連続登録に対応。
- 取得タイミングは開始時と中間試験／1次オーディション後の2択。
- 割合と初期ステータス加算を別々に選択。
- 条件の AND 判定は同一メモリー内で実施。
- PC では表、画面幅900px 以下ではメモリー単位のカード表示。
- 保存失敗時は入力を保持し、別タブとの競合時は上書きを拒否。
- JSON の出力と、検証・確認後の全件置換に対応。

画像、ログイン、同期、共有、OCR、有用度評価は対象外です。
固有・サポート・基本・レジェンドカード、ボーナス以外の通常アビリティも対象外です。
上記の対象外項目を含むメモリーでは、その項目を省略して記録します。

## ローカル起動

```bash
bun install --frozen-lockfile
bun run dev
```

表示された URL を開いてください。既定は `http://127.0.0.1:5173` です。
ポート使用中の場合、Vite は空いているポートを選びます。
固定したい場合は `bun run dev --port 5174 --strictPort` のように指定してください。

`localhost` と `127.0.0.1`、異なるポートは保存領域が別です。
いつも同じ URL でアクセスし、環境を移すときはバックアップを使用してください。
プライベートブラウジングの保存領域は終了時に削除される場合があります。

コンテナでは `bun run dev --host 0.0.0.0` とポート転送を使います。
ブラウザからは `localhost` または HTTPS で接続してください。
UUID の生成にはセキュアコンテキストが必要です。

## 提供された画像に対応する登録例

画像そのものはリポジトリに取り込んでいません。
`/memories/new?card=card-295` で、次の内容を選択できます。

| 項目 | 選択内容 |
| --- | --- |
| 獲得カード | スポットライト+ |
| 取得タイミング | 中間試験／1次オーディション後に獲得 |
| カスタム | 好調+、2段階 |
| HIF の発動対象 | ひと呼吸 |
| HIF 効果 | 試験ごと1回、山札か捨札の眠気をランダムに除外 |
| Vo | 割合0%、初期+15 |
| Da | 割合0%、初期+20 |
| Vi | 割合0%、初期+15 |

スポットライト+は好調6ターンです。
カスタム `custom-52` の2段階による+3ターンを加えると、画像の9ターンと一致します。
アプリは最終カード効果を計算せず、カスタムの種類と段階を記録します。
取得タイミングはカード効果の「開始時手札に入る」とは別の項目です。

## ゲーム仕様の扱い

- カスタムの対応関係と段階数は、同梱マスターで管理。
- カスタムの合計段階は R が3、SR が2、SSR が1。未強化カードはカスタムなし。
- HIF の発動対象は獲得カードと独立した選択。同一プランの候補を表示。
- 共通カードからはプロデュースのプランを特定できないため、HIF は全プランの候補を表示。
- HIF の効果と試験内発動回数は対象カードごとに固定。HIF 自体は0〜1個。
- ボーナスは各属性につき、割合と初期加算をそれぞれ0〜1個記録。
- 0以外のボーナス1項目を1枠として、HIF ありは最大3枠、なしは最大5枠。
- その他の通常アビリティは記録しないため、ボーナス枠は必ず埋める必要がない。
- 割合は0 / 1.4 / 2.1 / 2.8 / 3.5%、初期加算は0 / 10 / 15 / 20 / 25。

これは登録可能な値と組み合わせの検証です。
プロデュース評価別の抽選確率や取得可否までは再現していません。
未確認の例外や新規追加カードは、根拠とマスターを更新してから対応してください。

## バックアップと復元

1. `/settings` で「JSON をダウンロード」を選びます。
2. ダウンロードフォルダーに JSON ファイルがあることを確認します。
3. 復元先でファイルを選択すると、形式・バージョン・ID・値・組み合わせを検証します。
4. 件数と出力日時を確認し、「全件置換の確認へ」を選びます。
5. 確認ダイアログで「全件を置き換える」を選ぶと、1トランザクションで復元します。

インポートは10MB 以下の JSON に対応します。
0件のバックアップは全件削除と同じ結果になるため、件数を必ず確認してください。
検証失敗、キャンセル、書き込み失敗の場合、既存のデータは変更されません。
エクスポート日時は出力操作の記録です。ダウンロード完了を検知した日時ではありません。
復元後は最終バックアップ日時を未出力に戻します。

### バックアップ形式

```json
{
  "app": "gakumas-produce-memory-deck",
  "schemaVersion": 1,
  "masterVersion": 1,
  "exportedAt": "2026-01-01T00:00:00.000Z",
  "memories": []
}
```

メモリーには UUID、カード ID、取得タイミング ID、カスタム ID と値 ID、HIF ID と値 ID、ボーナス、登録・更新日時を保存します。
HIF がない場合は `null`、カスタムがない場合は空配列です。
ボーナスの割合は百分率で保存します。たとえば `2.1` は2.1%です。
出力には未解決の参照も残しますが、復元時に不明な参照があればファイル全体を拒否します。
該当マスターを回復してから復元し、ファイル内の ID を推測で置き換えないでください。

### 保存失敗・競合・破損時

- 書き込みが成功するまで画面の保存済み状態を更新しません。
- 容量不足や保存禁止の場合、フォームの入力と確認ダイアログを残します。
- 別タブで更新があった場合、古いリビジョンによる書き込みを拒否します。
- 競合時は入力を控え、再読み込みしてからやり直してください。
- 未対応バージョンや構造不正の場合、新規保存と上書きを停止します。
- 読み込めないデータはエラー画面の「保存データの原本をダウンロード」で保全できます。
- 原本ダウンロードは修復用です。通常のバックアップ形式とは異なります。

IndexedDB が利用できない場合、揮発性ストレージへ自動的に切り替えることはありません。
ブラウザの容量確保や設定変更を試し、原本の保全前にサイトデータを削除しないでください。

## マスターの更新

| ファイル | 内容 |
| --- | --- |
| `src/data/skill-master.json` | カード、カスタム、対応関係、段階上限 |
| `src/data/hif-master.json` | HIF の発動対象、プラン、効果、回数 |
| `src/data/memory-options.json` | 選択肢、ボーナス、取得タイミング、全体バージョン |

同じ形式で選択肢を追加するとフォームと検索条件に反映されます。
ID は表示名から生成せず、既存 ID を維持してください。
カスタムの値 ID は段階、HIF の値 ID は固定効果の識別子です。

```bash
# マスターの編集後、このリポジトリのルートで実行
bun run format
bun run check
```

マスターを編集した後は、上記のコマンドで書式と整合性を検証してください。
既存の登録データから参照されるため、過去の定義を消してはいけません。
廃止された定義を残し、`retired: true` にする作業が必要です。
ボーナス値の廃止は `values` に値を残したまま `retiredValues` に追加します。
既存データの表示とバックアップ復元では廃止済みの選択肢を許可し、新規選択は止めます。

HIF は独立したマスターで管理しています。
`create-hif-master.ts` は候補の対応表を再生成したい場合だけ実行してください。
このアプリにはゲーム画像を含めていません。

### バージョンと移行方針

初期保存形式は `schemaVersion: 1`、IndexedDB の DB バージョンは1です。
移行対象となる旧アプリ形式は存在しません。未知のバージョンを推測で変換しません。
全体マスターバージョンは `memory-options.json` の `version` で管理します。
各マスターファイルの `version` はそのファイルの構造バージョンです。

選択肢の追加・廃止では全体マスターバージョンを上げ、旧 ID の定義を保持してください。
新しい効果構造などで保存形式を変更するときは、次の手順を守ります。

1. 新しいスキーマと旧形式からの明示的な変換を定義する。
2. 旧バックアップのテストデータを使い、値を失わないことを検証する。
3. 変換・検証の成功後だけ、1トランザクションで新形式を保存する。
4. 失敗時は旧形式の原本を残し、ダウンロードできる状態を維持する。

## 実装の配置

- `src/domain/`: マスター検証、メモリー制約、検索、バックアップ形式。
- `src/storage/`: 保存先のインターフェース、IndexedDB 実装、React への接続。
- `src/pages/`: 一覧、登録・編集、バックアップ画面。
- `src/components/`: 比較・選択・確認用の共通 UI。
- `src/components/ui/`: shadcn/ui の生成コンポーネント（Base UI 版）。
- `tests/`: 本番ビルドを使った Playwright テスト。

UI は白と青灰を基調にし、Vo・Da・Vi の色と文字ラベルを併用しています。
日本語見出しには丸みのある書体、ボーナスには桁の揃う数値を使用します。
選択欄はモバイルとキーボード操作を優先したネイティブ要素です。
ボタン・バッジ・確認ダイアログは shadcn/ui を使用しています。

## 検証コマンド

```bash
bun run validate:master
bun run typecheck
bun run test
bun run build
bun run format:check
bunx playwright install chromium
bun run test:e2e
```

単体テストでマスターの参照、不正な組み合わせ、同一メモリー検索、廃止値、トランザクション失敗を検証します。
E2E テストでは PC とスマホ幅の Chromium で、登録、再読み込み、編集、複製、削除、JSON 復元を確認します。
保存失敗時の入力保持、別タブの競合、不正インポート、未知の保存形式、キーボード操作、横スクロールも検証対象です。
Safari、Firefox、実機のプライベートモードは未検証です。

E2E 用ポートは `4179` 固定です。使用中の場合はテストが失敗し、他のサーバーを再利用しません。
スクリーンショットと失敗時のトレースは `test-results/` に出力します。
テストは別ブラウザコンテキストで実行し、手動確認用ブラウザのデータは変更しません。

## 将来のCloudflare公開手順（未実行）

公開候補は Cloudflare Pages の静的配信です。D1 や API は不要です。
以下はアカウントとデプロイ権限を用意できた後の手順です。今回のローカル実装では実行していません。

1. `bun run check` と `bun run test:e2e` を実行する。
2. Cloudflare ダッシュボードの Workers & Pages から Pages の Direct Upload を作成する。
3. プロジェクト名を指定し、ビルド済みの `dist/` をアップロードする。
4. 公開操作後、提供された `<project>.pages.dev` を開く。独自ドメインは不要。
5. `/memories/new`、実在 ID の `/memories/:id/edit`、`/settings` を直接開き、再読み込みを確認する。
6. 公開先で登録・編集・バックアップを確認する。ローカルのデータ移動は JSON を使用する。

Pages はルートに `404.html` がない場合、SPA として未一致パスをルートへ返します。
この構成には `404.html` を置いていません。
他の静的サーバーを使う場合は、未一致パスを `index.html` に戻す設定が必要です。
SPA のエラー画面はアプリ側で表示します。
